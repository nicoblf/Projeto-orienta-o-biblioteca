Introdução

Na Fase 1 identificamos que a biblioteca, de pequeno porte, controla o acervo e os empréstimos em fichas de papel ou em planilha. Esse processo manual provoca exemplares sem rastreabilidade, atrasos que ninguém percebe, multas calculadas de cabeça, ausência de fila de reservas e a necessidade de ir até a biblioteca apenas para saber se um livro está disponível. Na Fase 2 transformamos esse problema em requisitos (RF01 a RF11), casos de uso, um Diagrama de Classes e uma arquitetura em camadas empacotada em contêineres Docker.

Esta Fase 3 entrega a primeira versão funcional do sistema. Ela registra o acervo (títulos e cópias físicas), os leitores e toda a circulação de exemplares, e aplica automaticamente as regras de empréstimo definidas nas fases anteriores: o exemplar precisa estar livre, o leitor não pode ter atraso nem multa em aberto, o limite de obras da categoria é respeitado, a data de devolução é calculada sozinha e a multa é gerada na devolução com atraso. A consulta ao acervo é pública, pelo navegador, sem login.

O sistema foi construído com o backend em Java, onde ficam todas as classes do modelo e as regras de negócio, e a interface em TypeScript, que roda no navegador e conversa com o backend por uma API REST. Os dados ficam gravados em um banco PostgreSQL. Tudo roda em três contêineres Docker, exatamente como a arquitetura da Fase 2 previa.

1.3 Implementação das classes

As classes do pacote backend/src/biblioteca/modelo correspondem uma a uma às classes do Diagrama de Classes da Fase 2, com os mesmos nomes, atributos, métodos e relacionamentos. Todos os atributos são privados (encapsulamento) e as regras de negócio ficam dentro dessas classes. Por exemplo, quem decide se um leitor pode emprestar é o próprio Leitor, e quem calcula o atraso é o próprio Emprestimo.

Trechos de código

Bibliotecario.registrarEmprestimo — regras RF05, RF07 e RF08

public Emprestimo registrarEmprestimo(Leitor leitor, Exemplar exemplar, LocalDate dataEmprestimo) {
    if (!exemplar.estaDisponivel()) {
        throw new RegraNegocioException("O exemplar " + exemplar.getCodigoTombo()
                + " não está disponível (situação: " + exemplar.getSituacao() + ").");
    }
    if (leitor.possuiPendencias()) {
        throw new RegraNegocioException(leitor.getNome() + " possui atraso ou multa em aberto.");
    }
    if (!leitor.podeEmprestar()) {
        throw new RegraNegocioException(leitor.getNome() + " atingiu o limite de "
                + leitor.getCategoria().getLimiteObras() + " obra(s) emprestada(s).");
    }
    Emprestimo emprestimo = new Emprestimo(leitor, exemplar, this, dataEmprestimo);
    exemplar.alterarSituacao(SituacaoExemplar.EMPRESTADO);
    leitor.adicionarEmprestimo(emprestimo);
    return emprestimo;
}

Leitor — pendências e limite (RF08)

public boolean possuiPendencias() {
    for (Emprestimo e : emprestimos) {
        if (e.estaAtrasado()) return true;
        if (e.getMulta() != null && !e.getMulta().isPaga()) return true;
    }
    return false;
}

public boolean podeEmprestar() {
    return !possuiPendencias() && qtdEmprestimosAtivos() < categoria.getLimiteObras();
}

Emprestimo — devolução, atraso e multa automática (RF06, RF09)

public void registrarDevolucao(LocalDate data) {
    if (!estaAtivo()) {
        throw new RegraNegocioException("Este empréstimo já foi devolvido em " + dataDevolucao + ".");
    }
    this.dataDevolucao = data;
    if (exemplar.getSituacao() == SituacaoExemplar.EMPRESTADO) {
        exemplar.alterarSituacao(SituacaoExemplar.DISPONIVEL);
    }
    if (diasAtraso() > 0) {
        this.multa = new Multa(this);          // valor = dias de atraso × multa diária da categoria
    }
}

public int diasAtraso() {
    LocalDate referencia = estaAtivo() ? LocalDate.now() : dataDevolucao;
    long dias = ChronoUnit.DAYS.between(dataPrevista, referencia);
    return dias > 0 ? (int) dias : 0;
}

Multa.calcularValor e Livro.qtdDisponiveis

public double calcularValor() {                       // Multa
    double bruto = emprestimo.diasAtraso() * emprestimo.getLeitor().getCategoria().getValorMultaDiaria();
    return Math.round(bruto * 100.0) / 100.0;
}

public int qtdDisponiveis() {                         // Livro
    int total = 0;
    for (Exemplar e : exemplares) {
        if (e.estaDisponivel()) total++;
    }
    return total;
}

Como a multa funciona: enquanto o livro não é devolvido, o empréstimo aparece como "Atrasado (N dias)" com a multa estimada do dia (N × valor diário da categoria). A multa real é gerada no momento da devolução, com o valor fixado naquele dia, e bloqueia novos empréstimos e renovações até que o bibliotecário registre o pagamento. 1.6 Dificuldades encontradas e soluções adotadas

DificuldadeSolução adotada
Separar título de cópia física (dificuldade 3 da Fase 1)Livro e Exemplar como classes distintas, ligadas por composição. A disponibilidade é calculada contando os exemplares DISPONIVEL, e o empréstimo é sempre de um exemplar específico (pelo código de tombo).
Impedir que dois atendimentos emprestem o mesmo exemplar ao mesmo tempoDuas camadas de proteção: a validação e a gravação ocorrem em um bloco synchronized no Roteador, e o PostgreSQL tem um índice único parcial que proíbe dois empréstimos em aberto do mesmo exemplar. Testamos com duas requisições simultâneas: uma retornou sucesso (201) e a outra foi recusada (422).
Onde colocar as regras de negócioDecidimos manter as regras nas classes do modelo (Leitor.podeEmprestar(), Emprestimo.diasAtraso(), Exemplar.registrarBaixa()), como o diagrama sugere. Os serviços apenas localizam objetos e chamam esses métodos.
Reconstruir os objetos a partir do bancoCriamos métodos restaurar(...) e uma carga em ordem de dependência (categorias, usuários, livros, exemplares, empréstimos, multas). Testado reiniciando apenas o backend: painel, multas e bloqueios continuaram idênticos.
Backend subindo antes do banco estar prontoHealthcheck no contêiner do banco, depends_on com condição de saúde no Docker Compose e novas tentativas de conexão no Banco, com a mensagem do erro no log.
Driver JDBC não encontrado dentro do contêinerA pasta de bibliotecas era criada com permissão errada. Corrigimos o Dockerfile para criar a pasta antes de baixar o driver.
nginx sem encontrar o backend na partidaConfiguramos o resolvedor de nomes do Docker no nginx, para que ele resolva o endereço do backend a cada requisição.
Testar atraso e multa sem esperar diasMétodos que recebem a data e carga inicial com um empréstimo já atrasado e uma multa em aberto. Assim as regras aparecem na hora da demonstração.
Multa "invisível" enquanto o livro não voltaPela regra, a multa só existe após a devolução, e o leitor atrasado não via valor nenhum. Criamos a multa estimada e faixas de aviso para o leitor e para a equipe, sem mudar a regra da Fase 2.
Acentos corrompidosGarantimos UTF-8 na compilação Java (-encoding UTF-8), nas respostas HTTP e no banco. A busca do acervo compara textos sem acento, então "programacao" encontra "Programação".
Segurança das senhas e dos dadosPBKDF2 com sal aleatório; mensagem idêntica para e-mail inexistente e senha errada; a consulta pública nunca devolve dados de leitores; todo texto vindo do servidor é escapado antes de entrar no HTML.
Trabalhar sem bibliotecas externasEscrevemos um leitor/escritor de JSON mínimo (Json.java), um roteador HTTP próprio e gráficos em HTML/SVG. Isso aumentou o código, mas deixou claro o papel de cada classe.

Resumo dos resultados

  • Todas as funcionalidades da versão inicial (RF01 a RF10) estão implementadas e demonstradas, com as regras de negócio dentro das classes do modelo.
  • O sistema roda em três contêineres (interface, backend e banco), como a arquitetura da Fase 2 previa, e os dados persistem no PostgreSQL.
  • As 29 verificações automáticas das regras passam.
  • Além do mínimo, foram entregues: autocadastro de leitor, painel com gráficos, filtros do acervo, busca de leitores, avisos de atraso com multa estimada e cadastro de telefone.
  • Ficam para as próximas versões: reservas (RF11), backup automático, avisos por e-mail, relatórios, LGPD (exclusão/anonimização) e HTTPS.
